## 1. Overview

Vault provisioning is the process of registering a new physical SmartVault device (ESP32-based hardware) to a user's account. Because the ESP32 has no pre-configured network credentials and no knowledge of which user owns it, provisioning must bridge three separate systems: the mobile app (authenticated user), the ESP32 hardware (unauthenticated device), and the backend (source of truth).

The flow works as follows:

1. The user taps an NFC card on the vault, which signals the ESP32 to enter Wi-Fi Access Point (AP) mode.
2. The user connects their phone to the ESP32's temporary Wi-Fi network and fills out a captive portal form — providing home Wi-Fi credentials, a vault name, and a short-lived **provisioning token** generated by the backend.
3. The ESP32 connects to the home network and calls a token-authenticated backend endpoint to complete registration.
4. The backend validates the token, resolves the owner, creates the vault record, and notifies the mobile app via WebSocket.

This design avoids requiring the ESP32 to handle JWTs or long-lived secrets. The provisioning token acts as a one-time, time-limited bridge between the authenticated mobile session and the unauthenticated hardware device.

## 3. Step-by-Step Breakdown

### Phase 1 — Mobile App Requests a Provisioning Token

**Step 1 — User initiates provisioning**
The user opens the SmartVault mobile app (already logged in) and taps **"Add Vault"**. The app prepares to generate a provisioning token before the user interacts with the hardware.

**Step 2 — App calls the token endpoint**
The app sends an authenticated request to the backend:
```
POST /api/v1/vaults/provisioning-token
Authorization: Bearer <access_token>
```
The JWT is used to identify the user. No request body is needed.

**Step 3 — Backend generates and stores the token**
The backend generates a short alphanumeric token (e.g., `A3F9K2`), stores the mapping `{ token → user_id }` in Redis with a 5-minute TTL, and returns the token to the app.

**Step 4 — App displays the token**
The app shows the token prominently (e.g., large text, easy to read). The user will need to type this into the ESP32's captive portal form.

---

### Phase 2 — Hardware Enters AP Mode

**Step 5 — User taps NFC card on the vault**
The ESP32's NFC scanner detects the tap. This is the hardware trigger that signals the device to begin provisioning mode.

**Step 6 — ESP32 enters Wi-Fi AP mode**
The ESP32 stops any existing Wi-Fi connection and broadcasts a temporary Wi-Fi network:
- **SSID:** `SmartVault-<hardware_uuid_short>` (e.g., `SmartVault-DEADBEEF0001`)
- **Password:** None (open network) or a fixed default
- **IP:** `192.168.4.1` (ESP32 default AP gateway)

---

### Phase 3 — User Configures the Device

**Step 7 — User connects phone to the ESP32 AP**
The user opens their phone's Wi-Fi settings, finds `SmartVault-DEADBEEF0001`, and connects. The phone may automatically open a captive portal browser window.

**Step 8 — Captive portal loads**
The phone browser navigates to `192.168.4.1`. The ESP32 serves a simple HTML form page.

**Step 9 — User fills out the form**
The user enters:
- **Wi-Fi SSID** — their home network name
- **Wi-Fi Password** — their home network password
- **Provisioning Token** — the 6-character code from the mobile app
- **Vault Name** — an optional display name (e.g., "Bedroom Vault")

The user submits the form.

---

### Phase 4 — ESP32 Connects and Registers

**Step 10–11 — ESP32 exits AP mode and connects to home Wi-Fi**
The ESP32 receives the form data, shuts down the AP, and uses the provided SSID and password to connect to the user's home network.

**Step 12 — ESP32 calls the backend**
Once connected, the ESP32 sends a registration request to the backend (no JWT required):
```
POST /api/v1/vaults/provision-by-token
Content-Type: application/json

{
  "hardware_uuid": "DEADBEEF00010001",
  "vault_name": "Bedroom Vault",
  "provisioning_token": "A3F9K2"
}
```

---

### Phase 5 — Backend Processes Registration

**Step 13 — Backend validates the token**
The backend looks up the provisioning token in Redis. If found, it retrieves the associated `user_id`. If the token is missing or expired, the request is rejected with `401 Unauthorized`.

**Step 14 — Backend deletes the token**
The token is immediately deleted from Redis after retrieval. It is one-time use only.

**Step 15 — Backend creates the vault**
The backend calls the existing `ProvisionVault` use case with the resolved `owner_id`, `hardware_uuid`, and `vault_name`. The use case checks for duplicate `hardware_uuid` and creates the vault record in PostgreSQL.

**Step 16 — Backend emits a domain event**
A `VaultProvisionedEvent` is emitted, carrying the new vault's details. The event handler pushes a `VAULT_PROVISIONED` WebSocket message to the user's active mobile connection.

**Step 17 — Backend responds to ESP32**
The backend returns `201 Created` to the ESP32:
```json
{
  "vault_id": "uuid-...",
  "hardware_uuid": "DEADBEEF00010001",
  "vault_name": "Bedroom Vault",
  "status": "offline"
}
```

---

### Phase 6 — Mobile App Receives Confirmation

**Step 18 — Mobile app receives WebSocket event**
The mobile app's existing WebSocket connection (`WS /api/v1/ws/user`) receives:
```json
{
  "type": "VAULT_PROVISIONED",
  "payload": {
    "vault_id": "uuid-...",
    "hardware_uuid": "DEADBEEF00010001",
    "vault_name": "Bedroom Vault",
    "status": "offline",
    "provisioned_at": "2026-02-28T12:00:00Z"
  }
}
```

**Step 19 — App shows success**
The app displays a success screen and navigates the user to the vault detail view for the newly registered vault.

## 4. What Needs to Be Built

### Domain Layer

**New: `VaultProvisionedEvent` in `app/domain/events/vault_events.py`**

The file currently exists but is empty. A `VaultProvisionedEvent` dataclass needs to be added. It should carry:
- `vault_id`
- `owner_id`
- `hardware_uuid`
- `vault_name`
- `status`
- `provisioned_at` (timestamp)

This event is emitted after a vault is successfully created via the token-based flow and is consumed by the WebSocket notification handler.

---

### Application Layer

**New use case: `ProvisionVaultByToken` in `app/application/use_cases/provision_vault_by_token.py`**

This use case orchestrates the token-based provisioning flow:
1. Accepts `hardware_uuid`, `vault_name`, and `provisioning_token`
2. Calls `ProvisioningTokenStore.get_user_id(token)` — raises an error if not found/expired
3. Calls `ProvisioningTokenStore.delete(token)` — invalidates the token
4. Delegates to the existing `ProvisionVault` use case (or directly calls `VaultRepository.create`) with the resolved `owner_id`
5. Emits `VaultProvisionedEvent`
6. Calls `UserWebSocketManagerPort.send_to_user(owner_id, VAULT_PROVISIONED message)`

**New port: `ProvisioningTokenStore` in `app/application/ports/provisioning_token_store.py`**

An abstract interface with:
- `generate_and_store(user_id) -> str` — generates a token, stores `{token → user_id}` in Redis with TTL, returns the token
- `get_user_id(token) -> str | None` — retrieves the `user_id` for a token, returns `None` if expired or not found
- `delete(token) -> None` — removes the token from storage

**New port: `UserWebSocketManagerPort` in `app/application/ports/user_websocket_manager.py`**

An abstract interface for sending messages to connected user (mobile) clients:
- `send_to_user(user_id: str, message: dict) -> None`
- `is_user_connected(user_id: str) -> bool`

This is separate from the existing `WebSocketManagerPort`, which handles sending messages to vault devices.

---

### Infrastructure Layer

**New Redis adapter: `RedisProvisioningTokenStore` in `app/infrastructure/redis/provisioning_token_store.py`**

Implements `ProvisioningTokenStore` using Redis:
- Token generation: `secrets.token_urlsafe(4)` or similar to produce a short alphanumeric string
- Storage key pattern: `provisioning_token:<token>`
- TTL: 300 seconds (5 minutes)
- Uses `SET ... EX` for atomic write-with-expiry
- `get_user_id` uses `GET`; `delete` uses `DEL`

**Extend WebSocket manager: `app/infrastructure/websocket/manager.py`**

The existing manager handles vault device connections. It needs to be extended (or a new `UserConnectionManager` class added) to:
- Track connected user (mobile) WebSocket sessions keyed by `user_id`
- Implement `send_to_user(user_id, message)` — sends JSON to the user's active WebSocket if connected
- Implement `is_user_connected(user_id)` — checks if a user has an active connection

---

### API Layer

**New endpoint: `POST /api/v1/vaults/provisioning-token`** (in `app/api/v1/vaults.py`)

- Requires JWT authentication (`get_current_user_id`)
- Calls `ProvisioningTokenStore.generate_and_store(user_id)`
- Returns the generated token
- No request body

**New endpoint: `POST /api/v1/vaults/provision-by-token`** (in `app/api/v1/vaults.py`)

- No authentication required
- Accepts `hardware_uuid`, `vault_name`, `provisioning_token` in the request body
- Calls `ProvisionVaultByToken` use case
- Returns `201 Created` with vault details on success
- Returns `401 Unauthorized` if the token is invalid or expired
- Returns `409 Conflict` if `hardware_uuid` is already registered

---

### WebSocket Layer

**New message type: `VAULT_PROVISIONED`**

The existing WebSocket handler for user connections (`WS /api/v1/ws/user`) already supports `VAULT_STATUS_CHANGED` push events. A new outbound message type `VAULT_PROVISIONED` needs to be defined and sent when a vault is successfully provisioned.

The message shape is:
```json
{
  "type": "VAULT_PROVISIONED",
  "payload": {
    "vault_id": "string",
    "hardware_uuid": "string",
    "vault_name": "string",
    "status": "string",
    "provisioned_at": "ISO 8601 timestamp"
  }
}
```

No changes to the mobile subscription mechanism are needed — the app does not need to subscribe to a vault before receiving this event, since the vault does not yet exist on the client side.

## 5. New Endpoint Contracts

### `POST /api/v1/vaults/provisioning-token`

**Purpose:** Generate a short-lived provisioning token tied to the authenticated user.

**Authentication:** Required — JWT Bearer token in `Authorization` header.

**Request:**
```
POST /api/v1/vaults/provisioning-token
Authorization: Bearer <access_token>
```
No request body.

**Response — `201 Created`:**
```json
{
  "token": "A3F9K2",
  "expires_in_seconds": 300
}
```

**Error responses:**

| Status | Condition |
|--------|-----------|
| `401 Unauthorized` | Missing or invalid JWT |

---

### `POST /api/v1/vaults/provision-by-token`

**Purpose:** Register a new vault using a provisioning token. Called by the ESP32 after connecting to home Wi-Fi.

**Authentication:** None — this endpoint is intentionally public.

**Request:**
```
POST /api/v1/vaults/provision-by-token
Content-Type: application/json
```
```json
{
  "hardware_uuid": "DEADBEEF00010001",
  "vault_name": "Bedroom Vault",
  "provisioning_token": "A3F9K2"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `hardware_uuid` | string | Yes | Unique hardware identifier burned into the ESP32 |
| `vault_name` | string | No | Display name for the vault; defaults to `"My Vault"` if omitted |
| `provisioning_token` | string | Yes | Short-lived token generated by the mobile app |

**Response — `201 Created`:**
```json
{
  "vault_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "hardware_uuid": "DEADBEEF00010001",
  "vault_name": "Bedroom Vault",
  "status": "offline"
}
```

**Error responses:**

| Status | Condition |
|--------|-----------|
| `401 Unauthorized` | Token not found in Redis or expired |
| `409 Conflict` | `hardware_uuid` is already registered to an account |
| `422 Unprocessable Entity` | Missing or malformed request body fields |

## 6. ESP32 Contract

### Captive Portal HTML Form

The ESP32 serves a minimal HTML page at `http://192.168.4.1` when in AP mode. The form collects everything needed to complete provisioning.

**Form fields:**

| Field | Input Type | Name attribute | Required | Notes |
|-------|-----------|----------------|----------|-------|
| Home Wi-Fi SSID | `text` | `ssid` | Yes | The user's home network name |
| Home Wi-Fi Password | `password` | `wifi_password` | Yes | Hidden input |
| Provisioning Token | `text` | `provisioning_token` | Yes | 6-char code from mobile app |
| Vault Name | `text` | `vault_name` | No | Optional display name |

The form submits to the ESP32 itself (e.g., `POST http://192.168.4.1/configure`). The ESP32 firmware handles the submission internally — it does not forward the Wi-Fi password to the backend.

### What the ESP32 POSTs to the Backend

After connecting to home Wi-Fi, the ESP32 sends only the fields needed for vault registration. **Wi-Fi credentials are never sent to the backend.**

```
POST https://<backend-host>/api/v1/vaults/provision-by-token
Content-Type: application/json
```
```json
{
  "hardware_uuid": "DEADBEEF00010001",
  "vault_name": "Bedroom Vault",
  "provisioning_token": "A3F9K2"
}
```

The `hardware_uuid` is a value burned into the ESP32 firmware at manufacture time (or derived from the chip's MAC address / eFuse). It is not user-supplied.

### ESP32 Behavior on Backend Response

| Backend Response | ESP32 Action |
|-----------------|--------------|
| `201 Created` | Store `vault_id` locally; begin normal operation (connect to MQTT/WebSocket) |
| `401 Unauthorized` | Display error on captive portal: "Token invalid or expired. Please generate a new token in the app." |
| `409 Conflict` | Display error: "This device is already registered." |
| Network failure | Retry up to 3 times with exponential backoff; fall back to AP mode if all retries fail |

## 7. Security Considerations

### Provisioning Token

- **Short-lived:** Tokens expire after 5 minutes (Redis TTL). A user who generates a token but does not complete provisioning within that window must request a new one.
- **One-time use:** The token is deleted from Redis immediately after it is validated. Even if an attacker intercepts the token, it cannot be reused.
- **Entropy:** Tokens should be generated using a cryptographically secure random source (e.g., Python's `secrets` module). A 6-character alphanumeric token from a 36-character alphabet gives ~31 bits of entropy — sufficient for a short-lived, rate-limited token.
- **Scope:** A token is tied to exactly one `user_id`. It cannot be used to provision a vault under a different account.

### AP Mode (No TLS)

The ESP32 captive portal operates over plain HTTP (`192.168.4.1`) with no TLS. This is acceptable for the following reasons:

- The AP network is local and short-lived (only active during provisioning).
- The range of the AP is limited to the immediate physical area of the vault.
- The Wi-Fi password entered in the form is transmitted only between the user's phone and the ESP32 over this local link — it is never sent to the backend.
- The provisioning token has a 5-minute TTL and is one-time use, limiting the damage window if intercepted.
- Adding TLS to an ESP32 captive portal requires certificate management that is impractical for a school project scope.

For a production system, mitigations could include: WPA2-secured AP with a printed default password, or using BLE instead of Wi-Fi AP for credential transfer.

### `POST /vaults/provision-by-token` (Unauthenticated Endpoint)

Because this endpoint requires no JWT, it is a potential target for abuse. Mitigations:

- **Rate limiting:** Apply a strict rate limit (e.g., 10 requests per IP per minute) using a middleware or Redis-backed counter. This prevents brute-force guessing of provisioning tokens.
- **Token entropy:** As noted above, short-lived + high-entropy tokens make brute force impractical within the TTL window.
- **No sensitive data returned:** The endpoint returns only vault metadata. No user PII or credentials are exposed.

### Duplicate Registration

The existing `ProvisionVault` use case already checks for duplicate `hardware_uuid`. Attempting to register an already-provisioned device returns `409 Conflict` and does not consume the provisioning token (the token should be preserved so the user can retry with a different device if needed — this is an open question; see Section 8).

## 8. Open Questions

1. **Vault name timing — when should the user set it?**
   Currently the design has the user enter the vault name on the ESP32 captive portal form. An alternative is to have the user set the name in the mobile app before or after provisioning. The captive portal approach is simpler but means the user must type the name on a small HTML form. The app-side approach gives a better UX but requires the backend to accept a name update after the fact.

2. **Token display UX — how should the app present the token?**
   The token must be easy to read and type. Options include: large monospace text, a QR code the ESP32 could scan (requires a camera on the ESP32), or NFC-based transfer of the token (the NFC tap could carry the token, eliminating manual entry entirely). The current design assumes manual entry.

3. **ESP32 failure handling — what happens if the ESP32 fails to reach the backend?**
   If the ESP32 connects to home Wi-Fi but the backend call fails (network error, timeout, or `5xx`), the device is in an inconsistent state: it has Wi-Fi credentials but no vault record. The current design suggests retrying up to 3 times, then falling back to AP mode. However, if the provisioning token has expired during retries, the user must start over. A longer TTL or a retry-specific token refresh mechanism may be needed.

4. **Token TTL length — is 5 minutes enough?**
   Five minutes covers the typical provisioning flow but may be tight if the user is slow to connect to the AP or encounters Wi-Fi issues. A 10-minute TTL would be more forgiving with minimal additional security risk, given the token's one-time-use nature.

5. **What happens to the token if `409 Conflict` is returned?**
   If the `hardware_uuid` is already registered, should the provisioning token be consumed (deleted) or preserved? Consuming it prevents reuse but means the user must generate a new token if they want to try a different device. Preserving it allows retry but slightly extends the attack window.

6. **Should the mobile app poll or rely solely on the WebSocket event?**
   If the user's WebSocket connection drops between token generation and provisioning completion, the `VAULT_PROVISIONED` event will be missed. The app may need a fallback — e.g., polling `GET /api/v1/vaults` after reconnecting — to detect newly provisioned vaults.
